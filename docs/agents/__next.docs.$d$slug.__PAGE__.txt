<h2>Let an agent fix it (Claude Code skill)</h2>
<p>The package ships a <code>sluglist-fix</code> skill that reads <code>.sluglist/</code> and fixes the reported issues. It
arrives with <code>npx sluglist init</code> above, or on its own with:</p>
<pre class="shiki shiki-themes light-plus dark-plus" style="--shiki-light:#000000;--shiki-dark:#D4D4D4;--shiki-light-bg:#FFFFFF;--shiki-dark-bg:#1E1E1E" tabindex="0"><code><span class="line"><span style="--shiki-light:#795E26;--shiki-dark:#DCDCAA">npx</span><span style="--shiki-light:#A31515;--shiki-dark:#CE9178"> sluglist</span><span style="--shiki-light:#A31515;--shiki-dark:#CE9178"> init-skills</span></span></code></pre><p>That copies every bundled skill into <code>.claude/skills/</code>. Re-running it is safe: unchanged skills are
refreshed silently, and any you have edited are reported and left alone (<code>--force</code> replaces them).</p>

<summary>or copy manually</summary>

<pre class="shiki shiki-themes light-plus dark-plus" style="--shiki-light:#000000;--shiki-dark:#D4D4D4;--shiki-light-bg:#FFFFFF;--shiki-dark-bg:#1E1E1E" tabindex="0"><code><span class="line"><span style="--shiki-light:#795E26;--shiki-dark:#DCDCAA">mkdir</span><span style="--shiki-light:#0000FF;--shiki-dark:#569CD6"> -p</span><span style="--shiki-light:#A31515;--shiki-dark:#CE9178"> .claude/skills</span><span style="--shiki-light:#000000;--shiki-dark:#D4D4D4"> &#x26;&#x26; </span><span style="--shiki-light:#795E26;--shiki-dark:#DCDCAA">cp</span><span style="--shiki-light:#0000FF;--shiki-dark:#569CD6"> -r</span><span style="--shiki-light:#A31515;--shiki-dark:#CE9178"> node_modules/sluglist/skills/sluglist-fix</span><span style="--shiki-light:#A31515;--shiki-dark:#CE9178"> .claude/skills/</span></span></code></pre></details>

<p>Then, after clicking feedback, ask Claude Code to <em>&quot;fix feedback&quot;</em>: it reads each issue (comment,
selector, <code>element_text</code>, screenshot, <code>## Errors</code>), localizes and fixes the code, and writes a
<code>.done</code> report into the session folder.</p>
<p>Why it works well: <a href="/docs/artifacts/">each artifact</a> is written for a file-reading agent —</p>
<ul>
<li>a <strong>CSS selector</strong> plus <code>dom_path</code> and <code>element_text</code> localize the element;</li>
<li>a <strong>React component hint</strong> (<code>component: AnimalCard</code>, read from the fiber, no React dependency
needed) localizes the source file;</li>
<li><code>## Errors</code> carries recent console errors, uncaught exceptions and failed requests with relative
timestamps;</li>
<li><code>## Actions</code> carries the click/navigation trail, cross-referenced to record-mode frames.</li>
</ul>
<p>Works with any agent that can read files — the skill is a convenience, not a dependency.</p>
<h2>Generate a checklist from a branch (the other direction)</h2>
<p>The second bundled skill, <code>sluglist-checklist</code>, turns a branch diff into a client-facing acceptance
checklist (user-visible changes only, phrased for a non-developer), written to
<code>.sluglist/checklists/&lt;name&gt;.json</code> — which the widget loads with
<code>checklist: &quot;/checklists/&lt;name&gt;.json&quot;</code>. Ask Claude Code to <em>&quot;generate a checklist from this
branch&quot;</em>. See <a href="/docs/checklist/">Checklist mode</a>.</p>
<h2>The whole cycle — the <code>sluglist-loop</code> skill</h2>
<p>Four skills ship in the package: one per stage, plus one that owns the cycle.</p>
<table>
<thead>
<tr>
<th>Skill</th>
<th>Role</th>
</tr>
</thead>
<tbody><tr>
<td><code>sluglist-loop</code></td>
<td>Picks the intent, runs the stages in order, carries the evidence mode, and keeps fixing and re-testing until green when you ask for it. <strong>Start here.</strong></td>
</tr>
<tr>
<td><code>sluglist-checklist</code></td>
<td>Generate or maintain a checklist: branch / re-test / smoke / regression / scenario.</td>
</tr>
<tr>
<td><code>sluglist-qa</code></td>
<td>Browser QA: no fail without a screenshot, no pass without performing the check.</td>
</tr>
<tr>
<td><code>sluglist-fix</code></td>
<td>Fix what failed, plus <code>fixes.yaml</code> (<code>fixed</code> | <code>wontfix</code> | <code>needs_info</code>).</td>

<p>Ask for <em>&quot;run the QA loop on this branch&quot;</em> and the orchestrator does the rest: checklist → QA run →
<code>npx sluglist report</code> → (on request) fix → re-test → final report. Project specifics it needs — base
branch, how to run and sign in, hard limits, evidence mode, loop limits — come from
<a href="/docs/project-conventions/"><code>.sluglist/PROJECT.md</code></a>, not from editing the skills.</p>
<h2>Until green — <code>npx sluglist status</code></h2>
<p>Ask for the fixes too — <em>&quot;QA this branch and fix everything until it passes&quot;</em> — and the cycle
repeats: QA finds failures, the fix skill resolves them, a re-test round checks the fixes. What keeps
that honest is a decision point the agent cannot answer from memory:</p>
<pre class="shiki shiki-themes light-plus dark-plus" style="--shiki-light:#000000;--shiki-dark:#D4D4D4;--shiki-light-bg:#FFFFFF;--shiki-dark-bg:#1E1E1E" tabindex="0"><code><span class="line"><span style="--shiki-light:#795E26;--shiki-dark:#DCDCAA">npx</span><span style="--shiki-light:#A31515;--shiki-dark:#CE9178"> sluglist</span><span style="--shiki-light:#A31515;--shiki-dark:#CE9178"> status</span></span></code></pre><pre class="shiki shiki-themes light-plus dark-plus" style="--shiki-light:#000000;--shiki-dark:#D4D4D4;--shiki-light-bg:#FFFFFF;--shiki-dark-bg:#1E1E1E" tabindex="0"><code><span class="line"><span>.sluglist — 1 chain, 2 sessions</span></span>
<span class="line"><span></span></span>
<span class="line"><span>release-2026-08 · branch · 3 items</span></span>
<span class="line"><span>  1  session-2026-08-15-tw1w  1 pass · 1 fail · 1 not tested  ·  1 fixed</span></span>
<span class="line"><span>  2  session-2026-08-15-jtyf  0 pass · 1 fail · 0 not tested  ·  no fix pass yet</span></span>
<span class="line"><span></span></span>
<span class="line"><span>  still failing (1)</span></span>
<span class="line"><span>    csv-columns — for the next fix pass · failed in 2 rounds · issue 01</span></span>
<span class="line"><span>      "The CSV has every expected column"</span></span>
<span class="line"><span></span></span>
<span class="line"><span>  not tested (1) — email-receipt</span></span>
<span class="line"><span></span></span>
<span class="line"><span>verdict: stalled — 1 item failed in 2 or more rounds — a fix pass has already been tried</span></span></code></pre><p>Everything is derived from artifacts already on disk: the verdicts in <code>session.yaml</code>, the resolutions
in <code>fixes.yaml</code>, and the <code>retest_of</code> chain linking round 2 back to round 1. No new file, no state to
keep in sync.</p>
<table>
<thead>
<tr>
<th>Verdict</th>
<th>Meaning</th>
<th>What the loop does</th>
</tr>
</thead>
<tbody><tr>
<td><code>green</code></td>
<td>Nothing is failing</td>
<td>Stop; hand over the report.</td>
</tr>
<tr>
<td><code>continue</code></td>
<td>Failures a fix pass can still act on</td>
<td>Another round, if the budget allows.</td>
</tr>
<tr>
<td><code>stalled</code></td>
<td>Every remaining failure already survived a fix pass</td>
<td>Stop; hand the list to a human.</td>
</tr>
<tr>
<td><code>blocked</code></td>
<td>Everything left is <code>wontfix</code> / <code>needs_info</code></td>
<td>Stop; those are the owner&#39;s calls.</td>
</tr>
<tr>
<td><code>empty</code></td>
<td>No sessions on disk</td>
<td>Nothing ran.</td>
</tr>
</tbody></table>
<p><code>--json</code> gives an agent the same result as data; <code>--all</code> includes older chains; a session folder as
the argument restricts the report to the chain containing it. It works for the plain dev loop too,
where the work items are the issues themselves rather than checklist verdicts.</p>
<p>The loop&#39;s ceiling is <strong>3 QA rounds</strong> by default — the first pass plus two fix→re-test rounds — and
it stops early on <code>stalled</code> or <code>blocked</code> rather than grinding the same item. Both are set in
<a href="/docs/project-conventions/"><code>PROJECT.md</code></a>. And the rule that makes the whole thing trustworthy: the
loop may never make a run green by editing a checklist item or recording <code>wontfix</code> to get out — green
is a fact about the app, not a target.</p>
