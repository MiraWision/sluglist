1a:T2e27,<h2>Capture modes</h2>
<ul>
<li><strong>fullpage</strong> — the whole scrollable document</li>
<li><strong>area</strong> — drag a rectangle and crop to it</li>
<li><strong>element</strong> — hover to highlight, click to capture a single element (records its CSS selector)</li>
<li><strong>comment only</strong> — no screenshot</li>
</ul>
<p>The menu lists them in that order (plus <strong>Record steps</strong>), most-used first, with <code>1</code>–<code>5</code> hotkeys
following the position.</p>
<p>Each screenshot can be annotated before sending (arrow, box, text; color; undo), with keyboard
shortcuts (A / B / T, Ctrl/Cmd+Z, Esc, click backdrop to close), and an issue can carry multiple
screenshots.</p>
<p><strong>When a screenshot fails, the issue still goes.</strong> A render can die on the browser&#39;s terms — a
webfont that never resolves, a canvas the browser refuses to encode, a render that hangs. Any of
those (plus a render that comes back blank, and anything slower than 8s) is caught: the reporter
sees a quiet <em>&quot;Screenshot failed — sending without it&quot;</em>, keeps everything they typed, and the issue
is delivered comment-only carrying <code>screenshot_failed: true</code> and <code>screenshot_error: &quot;&lt;why&gt;&quot;</code> in its
frontmatter. In record mode a failed frame is skipped and the recording continues, with the gap
marked in <code>## Actions</code>. Nothing about a report is ever lost to a picture that would not render.</p>
<pre><code class="language-ts">createFeedbackWidget({
  connectors: [/* … */],
  capture: { timeoutMs: 8000, detectBlank: true },  // defaults; both optional
});
</code></pre>
<p>Raise <code>timeoutMs</code> if you capture very long pages at high DPR.</p>
<h2>Action trail &amp; record mode</h2>
<p>Some bugs need a sequence, not a single screenshot. sluglist has two layers for that.</p>
<p><strong>Action trail</strong> (always on) keeps a small ring buffer of recent actions — clicks, SPA navigations,
submits, typing — and attaches them to every issue as a <code>## Actions</code> section (plus <code>actions_count</code>):</p>
<pre><code class="language-markdown">## Actions
- [45s before report] navigate /animals → /animals/128
- [12s before report] click button[aria-label=&quot;Save&quot;] (&quot;Save&quot;)
- [11s before report] type (12 chars) input#email
- [10s before report] submit form[data-testid=&quot;animal-form&quot;]
</code></pre>
<p><strong>PII rule (independent of any privacy setting):</strong> the trail records the <em>fact and place</em> of an
action, never the entered content. <code>type</code> logs only a character count; password fields aren&#39;t
logged at all by default; navigation paths drop the query string.</p>
<p><strong>Record mode</strong> turns a sequence into steps-to-reproduce <em>with images</em>. Click <strong>Record steps</strong>, do
the thing, then <strong>Stop &amp; describe</strong>. A frame is captured at the start and on each click /
navigation / submit (not typing). Each Record→Stop cycle is one <strong>clip</strong>: its frames go to
<code>NN-slug-frames/clip-01/01.png …</code>, and the matching <code>## Actions</code> lines are tagged
<code>— clip N, frame NN</code>. Frames respect PII masking. Need a state the auto-capture misses (a hover
popover, a transient toast)? Hit <strong><code>+ Frame</code></strong> in the recording bar — or press <strong>S</strong> — to snap one
manually.</p>
<p>Recordings and screenshots mix in one issue: start a recording from an open draft (via
<code>+ Add screenshot</code> → <code>Record steps</code>) and it attaches as a <strong>new clip</strong> instead of replacing
anything. Record twice and you get two independent clips — <code>clip-01/</code>, <code>clip-02/</code> — never one
merged reel.</p>
<pre><code class="language-ts">createFeedbackWidget({
  project: &quot;my-app&quot;,
  connectors: [/* ... */],
  actions: { capture: true, bufferSize: 30, capturePasswords: false }, // defaults
  recording: { enabled: true, maxFrames: 30, frameMinInterval: 650 },  // defaults
});
</code></pre>
<p>Deliberately <strong>not</strong> built: session replay (rrweb), real video (<code>getDisplayMedia</code> /
<code>MediaRecorder</code>), or network capture. The output is artifacts for an agent to read, not a replay a
human scrubs.</p>
<h2>Error capture</h2>
<p>From the moment the widget initializes, sluglist keeps a small ring buffer of recent page errors
from four sources — <code>console.error</code>, uncaught <code>error</code> events, <code>unhandledrejection</code>, and <strong>failed
network calls</strong> — and attaches a snapshot to each issue as a <code>## Errors</code> section (with a relative
timestamp per entry) plus an <code>errors_count</code> field in the frontmatter. The original <code>console.error</code>
still runs, so nothing is swallowed.</p>
<p>Network capture wraps <code>fetch</code> and <code>XMLHttpRequest</code> and records <strong>only</strong> requests that finish with a
status ≥ 400 or a network error — method, path (no query), status and duration, never bodies,
headers or query strings:</p>
<pre><code>## Errors
- [4s before report] network: POST /api/animals → 500 (240ms)
</code></pre>
<pre><code class="language-ts">createFeedbackWidget({
  project: &quot;my-app&quot;,
  connectors: [/* ... */],
  errors: {
    capture: true,          // default; set false to disable entirely
    bufferSize: 20,         // default
    captureWarnings: false, // default; true also captures console.warn
    captureNetwork: true,   // default; wrap fetch/XHR for failed-request facts
  },
});
</code></pre>
<blockquote>
<p><strong>Note:</strong> error messages and stack traces can contain user data — in beta mode they may include
PII. Production stack traces are usually minified. Treat captured errors as diagnostic hints, not
ground truth; sluglist stores them verbatim and does not resolve source maps.</p>
</blockquote>
<h2>Reporter form fields</h2>
<p>Ask the reporter what only they can tell you. Optional — with no <code>form</code> the panel is exactly what
it was.</p>
<pre><code class="language-ts">createFeedbackWidget({
  connectors: [/* … */],
  form: [
    // Asked once, on the first issue of the session → session.yaml
    { id: &quot;email&quot;, label: &quot;Your email&quot;, type: &quot;email&quot;, scope: &quot;session&quot; },
    { id: &quot;environment&quot;, label: &quot;Device / browser&quot;, type: &quot;text&quot;, scope: &quot;session&quot; },
    // Asked on every issue → that issue&#39;s frontmatter
    { id: &quot;severity&quot;, label: &quot;How bad is it?&quot;, type: &quot;select&quot;,
      options: [&quot;blocking&quot;, &quot;annoying&quot;, &quot;cosmetic&quot;], required: true, scope: &quot;issue&quot; },
  ],
});
</code></pre>
<p><code>type</code> is <code>text | email | select | checkbox</code>. <code>required</code> blocks sending and highlights the row;
<code>email</code> is pattern-checked; values are capped at 500 characters; at most 8 fields (invalid ones are
dropped with a warning, never breaking the widget).</p>
<p><strong>Form values are never scrubbed</strong>, even under the production preset. A reporter who types their
address into a field labelled <em>Your email</em> is telling it to you on purpose; redacting it would make
the field pointless. The scrub stays where it belongs — on text lifted off the page.</p>
<h2>Attachments</h2>
<p>Let the reporter attach their own files: the screenshot they took on their phone, a console export,
the spreadsheet that is wrong. Three ways in, all going to the same place:</p>
<ol>
<li><strong>+ Attach file</strong> next to <em>+ Add screenshot</em>.</li>
<li><strong>Drag &amp; drop</strong> onto the open panel.</li>
<li><strong>Paste</strong> (Cmd/Ctrl+V) — the one that matters most in practice, because a client&#39;s evidence
usually arrives in their clipboard from a phone or an email.</li>
</ol>
<p>Attached <strong>images join the thumbnail row and annotate like any capture</strong> — you can put arrows on
their screenshot. Everything else becomes a tile with its type, name and size, removable with the ✕.</p>
<pre><code class="language-ts">createFeedbackWidget({
  connectors: [/* … */],
  attachments: {
    enabled: true,            // default true — but FALSE under preset: &quot;production&quot;
    maxFileSize: 10 * 1024 * 1024,
    maxFiles: 5,
    accept: [&quot;.log&quot;, &quot;image/*&quot;],   // optional: replaces the built-in whitelist
  },
});
</code></pre>
<p>Accepted by default: images (png, jpeg, webp, gif, heic), video (mp4, webm, mov), pdf, text (txt,
csv, json, md) and office (xlsx, docx). Checked on <strong>both</strong> the extension and the reported mime, so
a renamed binary is refused. <strong>Executables and archives are never accepted</strong> — not even through
<code>accept</code>. Over the size or count limit, the reporter gets a message naming the file and the actual
limit; nothing is compressed or transcoded on the client.</p>
<p>Files land next to the issue and are listed in its frontmatter. The reporter&#39;s own file name is
never used as a path — it is kept as data:</p>
<pre><code class="language-yaml">attachments:
  - file: 03-checkout-att-01.png
    mime: image/png
    size: 482112
    original_name: &quot;IMG_4021.png&quot;
</code></pre>
<blockquote>
<p><strong>Attachments default to OFF under <code>preset: &quot;production&quot;</code>.</strong> Accepting uploads from anonymous
users is a decision, not a default. Turn it on when you have decided your endpoint can take it —
and validate server-side regardless (see <a href="/docs/production/">Production</a>).</p>
</blockquote>
<h2>Mobile graceful mode</h2>
<p>On a coarse pointer (detected from the pointer, not the user agent — a touch laptop keeps the full
desktop UI) sluglist <strong>subtracts</strong> rather than reimplements:</p>
<ul>
<li>The menu offers <strong>full page</strong> and <strong>comment only</strong>. Area mode needs a drag the browser spends on
scrolling, and element mode is built on hover; both are hidden rather than offered and then
failing.</li>
<li><strong>Record mode is hidden.</strong> Frames captured mid-scroll are unreadable; deferred rather than
shipped bad.</li>
<li>Panels go full-width, controls reach 44px, the textarea scrolls itself clear of the keyboard,
inputs use 16px so iOS does not zoom in and strand the reporter, and the launcher clears the home
indicator (<code>safe-area-inset-bottom</code>).</li>
<li>Keyboard hints (the shortcut chips) are not shown to a device with no keyboard.</li>
</ul>
<p>The checklist panel is fully usable on a phone; the per-item report button is always visible there
instead of hover-revealed.</p>
<h2>Known limits</h2>
<p>Measured in Chromium 151, Firefox 153 and WebKit 26.5 (the Safari engine) against a page built out
of known DOM-to-canvas failure modes.</p>
<p><strong>Renders correctly in all three engines:</strong> webfonts, emoji, CSS <code>filter</code>, gradients,
<code>position: fixed</code>, long full-page captures, cross-origin images served with CORS headers, and the
annotation round-trip.</p>
<p><strong>Known limits — not fixable from here:</strong></p>
<ul>
<li><strong><code>backdrop-filter</code> is not rendered</strong> in any engine. The blur is dropped and the element paints
as if it had none.</li>
<li><strong>Cross-origin images served without <code>access-control-allow-origin</code> come out blank.</strong> The rest of
the page still captures.</li>
<li><strong>WebGL, <code>&lt;canvas&gt;</code> and video content</strong> do not render.</li>
