1a:T1a60,<p>Feedback normally fills a session <strong>from the bottom</strong> — the client freely creates issues. A
<strong>checklist</strong> fills it <strong>from the top</strong>: the developer pre-seeds a list of &quot;what shipped and what
to verify&quot;, and the client walks it with one natural motion — <strong>click a row to check it off; click
the slug button on a row to flag a problem</strong> (that opens the normal issue flow, linked back to the
item).</p>
<p>The panel is an accordion of sections that self-navigates: finish a section and it collapses,
opening the next one. A summary line (<code>5 of 12 checked · 2 issues · 7 left</code>) replaces a bare
counter, and the circle&#39;s badge counts what&#39;s left, turning to ✓ when everything is checked. The
result is a <strong>coverage map</strong> in <code>session.yaml</code>: what&#39;s confirmed, what was flagged (with links to
the issues), and what was never checked.</p>
<p>It&#39;s entirely opt-in: a second circle appears above the feedback button <strong>only</strong> when a checklist
is configured. Without one, the widget looks and works exactly as before.</p>
<pre><code class="language-ts">const widget = createFeedbackWidget({
  project: &quot;acme&quot;,
  connectors: [/* ... */],
  checklist: {
    id: &quot;export-release-2026-07&quot;,
    title: &quot;Export + notifications release&quot;,
    description: &quot;Walk each item and check it off. Flag anything that looks wrong.&quot;,
    sections: [
      {
        title: &quot;Export&quot;,
        items: [
          { id: &quot;export-button&quot;, title: &quot;On Reports, the Export button downloads a CSV&quot;, url: &quot;/reports&quot; },
          { id: &quot;csv-columns&quot;, title: &quot;The CSV has all the expected columns&quot;, hint: &quot;Open it in a spreadsheet&quot; },
          // Dynamic route: no fabricated id — a human hint + a wildcard match.
          { id: &quot;assessment-header&quot;, title: &quot;Opening any assessment shows the new header&quot;,
            hint: &quot;Open the dashboard and pick any assessment&quot;, url: &quot;/dashboard&quot;, url_match: &quot;/assessments/*&quot; },
        ],
      },
      { title: &quot;Notifications&quot;, items: [{ id: &quot;email-sent&quot;, title: &quot;An email arrives after an export&quot; }] },
    ],
  },
});
</code></pre>
<h2>Smart links</h2>
<p><code>url</code> must be a <strong>static</strong> route — it renders as an &quot;Open ↗&quot; chip that navigates there. For a
<strong>dynamic</strong> route (an id/uuid in the path) don&#39;t guess an id: give a human <code>hint</code> and a wildcard
<code>url_match</code> (<code>&quot;/assessments/*&quot;</code>). It never navigates — it just lights the item up with a &quot;You&#39;re
here&quot; tag when the tester is on a matching page. The two can coexist (a list <code>url</code> + a detail
<code>url_match</code>).</p>
<p>Pass a <strong>URL string</strong> instead of an object to fetch the checklist at init (<code>GET</code> → JSON of the same
shape) — handy when a skill generates it: <code>checklist: &quot;/checklist.json&quot;</code>. An unreachable or invalid
checklist warns and is skipped; capture still works.</p>
<h2>Verdicts: the coverage map</h2>
<p>Verdicts land in <code>session.yaml</code> (put-per-verdict, upserted on every click):</p>
<pre><code class="language-yaml">checklist:
  id: export-release-2026-07
  title: &quot;Export + notifications release&quot;
  items:
    - id: export-button
      section: &quot;Export&quot;
      title: &quot;On Reports, the Export button downloads a CSV&quot;
      verdict: pass
      issue: null
      ts: 2026-07-24T14:05:10Z
    - id: csv-columns
      section: &quot;Export&quot;
      title: &quot;The CSV has all the expected columns&quot;
      verdict: fail
      issue: &quot;03&quot;          # the issue that documents the failure
      ts: 2026-07-24T14:06:00Z
    - id: email-sent
      section: &quot;Notifications&quot;
      title: &quot;An email arrives after an export&quot;
      verdict: null        # not checked
      issue: null
      ts: null
</code></pre>
<h2>Generate a checklist from a branch</h2>
<p>The package ships a <code>sluglist-checklist</code> skill: point Claude Code at a branch and it builds a
client-facing checklist from the diff (user-visible pages/components/text only — refactors, tests
and config are excluded), grouped by feature and phrased for a non-developer, written to
<code>.sluglist/checklists/&lt;name&gt;.json</code>. Ask it to <em>&quot;generate a checklist from this branch&quot;</em>.</p>
<p>Five intents, one per source of truth: <code>branch</code> (the diff), <code>re-test</code> (a fixed session&#39;s
<code>fixes.yaml</code>), <code>smoke</code> (routes + docs), <code>regression</code> (the project&#39;s standing baseline), and
<code>scenario</code> (a written brief). The base branch a <code>branch</code> diff runs against comes from
<a href="/docs/project-conventions/"><code>.sluglist/PROJECT.md</code></a>.</p>
<h2>The regression checklist has a lifecycle</h2>
<p>Four of the five intents produce a list you use once. <code>regression</code> is different: it is a <strong>committed
baseline</strong> at <code>.sluglist/checklists/regression.json</code>, seeded once with the smoke algorithm and then
<strong>updated after each merge</strong> — ask for <em>&quot;update the regression checklist from this branch&quot;</em>.</p>
<p>An update is a diff of the list, not a regeneration:</p>
<ul>
<li><strong>Additions</strong> for user-visible surface the branch added — one or two loud checks per feature,
folded into an existing section when one fits.</li>
<li><strong>Removals</strong> for items whose surface the branch deleted — always <strong>proposed for you to confirm</strong>,
never applied silently.</li>
<li><strong>The ~30-item cap holds.</strong> If additions would push past it, the skill names which existing items
to cut instead of growing the file.</li>
<li><strong>Item ids stay stable</strong> for unchanged items, so verdicts recorded in past sessions still map to
them.</li>
</ul>
<h2>Scope — the checklist is a session input, verdicts are its output</h2>
<p>The checklist enters a session and the verdicts leave with it. There is <strong>no lifecycle beyond the
session</strong>: items are never reopened, verdicts never sync between sessions, nothing is stored as a
&quot;done on the server&quot;, and issues are never blocked on completing the checklist. Every session runs
the checklist from scratch. This is deliberate — it keeps sluglist a capture tool, not a workflow
tracker.</p>
